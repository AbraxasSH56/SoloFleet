# Anomaly deep review (once a day, System auditor role; run time follows the config `jobs.deepReview.time`; guarded by a trigger script)

> The words in code spans and quotation marks in these rules (status values, JSON keys, summary labels and so on) are the exact words the programs match; write them exactly as shown. The all-caps angle-bracket placeholders in the text (such as `<GUILD_ID>`, `<TIMEZONE>`, `<WORKSHOP_CHANNEL_ID>`) are filled in once at deployment time; the placeholders `<DATA_ROOT>` (data root) and `<PROJECT_ROOT>` (project root) are taken from the task message on every run and must not be replaced. See `jobs/README.md` for details.

This task uses the API credit that comes with a subscription (if your subscription plan includes one). When the credit runs out, stop; do not fall back to the subscription. For how to write the provider, see `config/examples/api-credit-providers.example.json`.

Applies to role: `system-auditor`. The task has a trigger script attached (`scripts/automation/deep-review-trigger.js`): it really runs only when the marker directory contains a marker with status "to-review" whose `found_at` is earlier than the cutoff point, or a marker with status "reviewing"; if there is none it is skipped and no quota is spent. The platform no longer delivers your reply for this round. The digest in the Workshop channel is sent as-is from the digest file by the publish script that you call as your last step (see common rules 5 and 8), as **a single separate message**, with the opening label "[Audit · Deep review · <BUSINESS_DATE>]".

## Parameters of this task
- Task folder: `audit/deep-review` (audit / anomaly deep review); `HM` = the config value `jobs.deepReview.time` (local time, time zone per the config `timezone`), `DOW=` (every day).
- Fixed location: Lounge channel ID `<LOUNGE_CHANNEL_ID>` (use it only when a marker points to a Lounge thread; see common rule 9).

### 2 Business date and cutoff point (compute once at the start of the task, write into the round record, never change afterwards)
- One round = task + business date. **Cutoff point = the scheduled time of that business date.** The business date is the local date of "the most recent scheduled time before this run started" (time zone per config `timezone`; `TZN` in the snippet below must be the same). Example: a patrol scheduled at 18:30 is re-run by hand at 09:00 the next day; the most recent 18:30 before that is the previous day, so the business date is the previous day.
- Every later step of the round (reading the increment, file names, report labels) uses the values in the round record and does not recompute from a new "now".
- Use the command below to compute it; do not work it out in your head. First give the two variables of this task (see the "Parameters of this task" section) in front of the command, for example `HM=18:30 DOW= sh -c '<the snippet below>'`; the weekly audit sets DOW to 0 (Sunday), the others leave it empty. The snippet prints one line with the business date and the cutoff point; the two labels in that line are `business_date=` and `cutoff=`. Read the two values after the labels.

```sh
# business-date-snippet begin
# Usage: set HM (scheduled time such as 18:30, from config jobs.<name>.time) and DOW (only the weekly audit sets it, Sunday is 0; leave empty for daily jobs) before running this snippet.
# TZN on the next code line is the time zone name filled in once at deployment (same as config timezone, e.g. UTC); it is not a variable passed in on each run.
# For tests, FAKE_NOW (seconds) stands in for "now"; do not set it in production.
TZN=<TIMEZONE>
NOW=${FAKE_NOW:-$(date +%s)}
BR() { TZ=$TZN date "$@"; }
D=$(BR -j -f %s "$NOW" +%Y-%m-%d)
for i in 0 1 2 3 4 5 6 7 8; do
  C=$(BR -j -f "%Y-%m-%d %H:%M:%S" "$D $HM:00" +%s)
  W=$(BR -j -f "%Y-%m-%d %H:%M:%S" "$D 12:00:00" +%w)
  if [ "$C" -le "$NOW" ] && { [ -z "$DOW" ] || [ "$W" = "$DOW" ]; }; then break; fi
  D=$(BR -j -v-1d -f "%Y-%m-%d %H:%M:%S" "$D 12:00:00" +%Y-%m-%d)
done
Z=$(BR -j -f %s "$C" +%z)
echo "business_date=$D cutoff=$(BR -j -f %s "$C" +%Y-%m-%dT%H:%M:%S)${Z%??}:${Z#???}"
# business-date-snippet end
```

### 3 The round record and "half-done"
- Each task has one file per round, `<DATA_ROOT>/audit/<TASK_FOLDER>/<BUSINESS_DATE>.json`, which records only how far the execution got. Format: `{"task":"…","business_date":"YYYY-MM-DD","cutoff":"…±HH:MM","previous_cutoff":"…","execution":"in-progress|done","done":{…},"updated_at":"…"}`. The offset in `cutoff` is the real UTC offset of the configured time zone.
- **Read the round record first.** Not there: create it with `execution` set to "in-progress". `execution: done`: do not redo the work (do not change the report, the digest or the round record); the patrol, deep review and weekly audit must still call the publish script under common rule 8, and the last reply is only the line the script printed; the daily audit replies with one sentence, "daily-audit <BUSINESS_DATE> finished". `execution` is "in-progress": continue from `done`; first re-check the current state of steps already done, and do not write or send them twice.
- Whether a report was delivered is not recorded here. The daily audit looks at the official run records. For the patrol, deep review and weekly audit, **the self-publish start business dates** are the three dates in the `EFFECTIVE_FROM` constant of the publish script `publish-self.py` (one each for patrol, deep review and weekly audit; normally the day you turned self-publishing on). Rounds before the start date are judged from the official run records; from the start date on, read the publish receipt `<DATA_ROOT>/audit/publish/receipts/<task>-<BUSINESS_DATE>.json` (it is the delivery-status record of the digest, not an account secret, so you may read it). **Trusted delivered** means: the file can be read in full; `task` and `business_date` agree with the file name; `account` is `default`; `channel` is `discord`; `target` is `channel:<WORKSHOP_CHANNEL_ID>`; `state` is "delivered"; `message_id` is a string of 17 to 20 digits; and the file `<task>-<BUSINESS_DATE>.receipt.txt` exists in the same folder. If any one of these fails it is "delivery-to-verify". If it is trusted-delivered but the `digest` in the receipt differs from `shasum -a 256` of the current digest file, write "the sent digest differs from the current file, to be verified". `ok` or `not-requested` in the official records cannot replace this judgment.

## What to do (in order)

### Step 1: Business date and the to-do list
- The trigger script appends the following after the task text: `business_date=…; cutoff=…; to_review=<file name>; to_continue=<file name (how to handle)>`; or "Condition check read incomplete: <reason>". **Use the business date and cutoff point in it directly**; do not recompute them; write them into the round record.
- **A forced manual run skips the trigger script**, so the information above is absent: work out the business date and cutoff point yourself per common rule 2 (`HM` = the config value `jobs.deepReview.time`), then list the to-do items yourself: in `<DATA_ROOT>/audit/anomaly-flags/`, the markers whose `status` is not "reviewed"; a marker with "to-review" whose `found_at` is earlier than the cutoff point is to review, and one with "reviewing (<date>)" is to continue.
- "Condition check read incomplete": check the marker directory yourself; do not treat it as having nothing to do.

### Step 2: Continue according to the round record
Read the round record `<DATA_ROOT>/audit/deep-review/<BUSINESS_DATE>.json` (common rule 3).
- For markers **to continue** (status "reviewing (<date>)"): look at the round record of **that day**. If it says `execution: done` (the trigger script writes "finish-up only (this round is already done; do not re-review the content)") -> only do the wrap-up (step 8), change the remaining markers to "reviewed", and **do not re-review the content**. If it is not done (the trigger script writes "continue the review (this round record is not done)") -> continue from the `done` of that day's round record, and review the parts not yet done as usual. If the trigger script writes "cannot tell (the round record of that day cannot be read; please check it yourself)", read that day's round record yourself and decide in the same way.
- Write the "list to review" into the round record, and do not change it afterwards.

### Step 3: Start work: change markers to "reviewing"
For the markers **to review** in this round, change the `status` to `reviewing (<BUSINESS_DATE>)` one by one, using exact replacement. Handle all "to-review" markers before the cutoff point at once, merged into a single deep review; the ones recorded after the cutoff point are left for the next day.

### Step 4: Review
For each marker: read the content in the marker; go back to the original record and verify it (if the marker points to a thread in the Lounge channel, handle it per common rule 9; read the related files, task records and task cards; read Discord with `openclaw message read …`, read-only, written the same way as step 5 of the daily audit); judge whether it is a real problem, how severe it is, and whom it should go to (the original owner of the item, the Controller, the owner). **You only read and draw conclusions; you do not handle anything**: do not change the files under review, do not assign work, do not send messages. If the evidence is insufficient, write "Could not verify (reason)" and draw no conclusion.

### Step 5: Write the full report
`<DATA_ROOT>/audit/deep-review/<BUSINESS_DATE>.md` (rewrite the whole file): one section per marker, with the event key, what was seen, what was verified (location of the evidence), the conclusion, the severity, and whom it is recommended to go to.

### Step 6: Write the digest
`<DATA_ROOT>/audit/deep-review/<BUSINESS_DATE>-summary.txt`: the first line is `[Audit · Deep review · <BUSINESS_DATE>]`; at most 12 lines, at most 1200 characters, plain text; the last line is `Full report: dataroot/audit/deep-review/<BUSINESS_DATE>.md`.

### Step 7: Change the round record to `execution: done`
### Step 8: Only **last**, change the markers to "reviewed"
For the markers handled in this round, change the `status` to `reviewed (<BUSINESS_DATE>)` one by one, using exact replacement. **The order is fixed: full report -> digest -> round record "done" -> markers "reviewed" -> call the publish script (common rules 5 and 8) -> final reply.** If interrupted midway, the next run continues according to step 2.
### Step 9: Call the publish script, final reply
Call the publish script per common rules 5 and 8; make the final reply just the one line the script outputs, with nothing else mixed in.
