# Anomaly deep review (异常深审) (once a day, System auditor role; run time follows the config `jobs.deepReview.time`; guarded by a trigger script)

> These rules are used together with their Chinese literals unchanged. The all-caps angle-bracket placeholders in the text (such as `<GUILD_ID>`, `<TIMEZONE>`, `<WORKSHOP_CHANNEL_ID>`) are filled in once at deployment time; the Chinese placeholders such as `<资料根>` (data root) and `<项目根>` (project root) are taken from the task message on every run and must not be replaced. The programs still match Chinese literal strings, so the Chinese literals in this file (status values, JSON keys, summary labels and so on) are kept in Chinese, with an English gloss in parentheses at first use. See `jobs/README.md` for details.

This task uses the API credit that comes with a subscription (if your subscription plan includes one). When the credit runs out, stop; do not fall back to the subscription. For how to write the provider, see `config/examples/api-credit-providers.example.json`.

Applies to role: `system-auditor`. The task has a trigger script attached (`scripts/automation/deep-review-trigger.js`): it really runs only when the marker directory contains a marker with status "待深审" (pending deep review) whose discovery time is earlier than the cutoff point, or a marker with status "深审中" (deep review in progress); if there is none it is skipped and no quota is spent. The platform no longer delivers your reply for this round. The digest in the Workshop channel is sent as-is from the digest file by the publish script that you call as your last step (see common rules 5 and 8), as **a single separate message**, with the opening label "【审计 · 异常深审 · <业务日期>】" (audit, anomaly deep review, business date).

## Parameters of this task
- Task folder: `审计/异常深审` (audit / anomaly deep review); `HM` = the config value `jobs.deepReview.time` (local time, time zone per the config `timezone`), `DOW=` (every day).
- Fixed location: Lounge channel ID `<LOUNGE_CHANNEL_ID>` (use it only when a marker points to a Lounge thread; see common rule 9).

### 2 Business date and cutoff point (compute once at the start of the task, write into the round record, never change afterwards)
- One round = task + business date. **Cutoff point = the scheduled time of that business date.** The business date is the local date of "the most recent scheduled time before this run started" (time zone per config `timezone`; `TZN` in the snippet below must be the same). Example: a patrol scheduled at 18:30 is re-run by hand at 09:00 the next day; the most recent 18:30 before that is the previous day, so the business date is the previous day.
- Every later step of the round (reading the increment, file names, report labels) uses the values in the round record and does not recompute from a new "now".
- Use the command below to compute it; do not work it out in your head. First give the two variables of this task (see the "Parameters of this task" section) in front of the command, for example `HM=18:30 DOW= sh -c '<the snippet below>'`; the weekly audit sets DOW to 0 (Sunday), the others leave it empty.

```sh
# business-date-snippet begin
# Usage: set HM (scheduled time such as 18:30, from config jobs.<name>.time) and DOW (only the weekly audit sets it, Sunday is 0; leave empty for daily jobs) before running this snippet.
# TZN on the next code line is the time zone name filled in once at deployment (same as config timezone, e.g. UTC); it is not a variable passed in on each run.
# For tests, FAKE_NOW (seconds) stands in for "now"; do not set it in production.
TZN=<TIMEZONE>
NOW=${FAKE_NOW:-$(date +%s)}
BR() { TZ=$TZN date "$@"; }
D=$(BR -j -f %s "$NOW" +%Y-%m-%d)
for i in 0 1 2 3 4 5 6 7 8; do
  C=$(BR -j -f "%Y-%m-%d %H:%M:%S" "$D $HM:00" +%s)
  W=$(BR -j -f "%Y-%m-%d %H:%M:%S" "$D 12:00:00" +%w)
  if [ "$C" -le "$NOW" ] && { [ -z "$DOW" ] || [ "$W" = "$DOW" ]; }; then break; fi
  D=$(BR -j -v-1d -f "%Y-%m-%d %H:%M:%S" "$D 12:00:00" +%Y-%m-%d)
done
Z=$(BR -j -f %s "$C" +%z)
echo "业务日期=$D 截止点=$(BR -j -f %s "$C" +%Y-%m-%dT%H:%M:%S)${Z%??}:${Z#???}"
# business-date-snippet end
```

### 3 The round record and "half-done"
- Each task has one file per round, `<资料根>/审计/<任务目录>/<业务日期>.json` (task folder / business date), which records only how far the execution got. Format: `{"任务":"…","业务日期":"YYYY-MM-DD","截止点":"…±HH:MM","上一截止点":"…","执行":"进行中|完成","已做":{…},"更新时间":"…"}` (keys: task, business date, cutoff point, previous cutoff point, execution = in progress | done, done-so-far, updated at). The offset in the cutoff point is the real UTC offset of the configured time zone.
- **Read the round record first.** Not there: create it with `执行` set to "进行中" (in progress). `执行: 完成` (done): do not redo the work (do not change the report, the digest or the round record); the patrol, deep review and weekly audit must still call the publish script under common rule 8, and the last reply is only the line the script printed; the daily audit replies with one sentence, "日审 <业务日期> 已完成" (daily audit <business date> completed). `执行` is "进行中": continue from "已做" (done so far); first re-check the current state of steps already done, and do not write or send them twice.
- Whether a report was delivered is not recorded here. The daily audit looks at the official run records. For the patrol, deep review and weekly audit, **the self-publish start business dates** are the three dates in the `EFFECTIVE_FROM` constant of the publish script `publish-self.py` (one each for patrol, deep review and weekly audit; normally the day you turned self-publishing on). Rounds before the start date are judged from the official run records; from the start date on, read the publish receipt `<资料根>/审计/发布/凭据/<任务>-<业务日期>.json` (it is the delivery-status record of the digest, not an account secret, so you may read it). **Trusted delivered** means: the file can be read in full; "任务" and "业务日期" agree with the file name; "账号" is `default`; "频道" is `discord`; "目标" is `channel:<WORKSHOP_CHANNEL_ID>`; "状态" is "已送达"; "消息编号" is a string of 17 to 20 digits; and the file `<任务>-<业务日期>.回执.txt` exists in the same folder. If any one of these fails it is "送达待核" (delivery unverified). If it is trusted-delivered but the "摘要指纹" (digest fingerprint) in the receipt differs from `shasum -a 256` of the current digest file, write "已发摘要与当前文件不同，待核" (the sent digest differs from the current file, to be verified). `ok` or `not-requested` in the official records cannot replace this judgment.

## What to do (in order)

### Step 1: Business date and the to-do list
- The trigger script appends the following after the task text: `业务日期=…；截止点=…；待审=<文件名>；待接=<文件名（处理方式）>` (business date=...; cutoff point=...; to review=<file name>; to take over=<file name (how to handle)>); or "条件检查读取不完整：<原因>" (condition check read incompletely: <reason>). **Use the business date and cutoff point in it directly**; do not recompute them; write them into the round record.
- **A forced manual run skips the trigger script**, so the information above is absent: work out the business date and cutoff point yourself per common rule 2 (`HM` = the config value `jobs.deepReview.time`), then list the to-do items yourself: in `<资料根>/审计/异常标记/` (audit / anomaly markers), the markers whose status is not "已深审" (deep reviewed); a marker with "待深审" whose discovery time is earlier than the cutoff point is to review, and one with "深审中（某日）" (deep review in progress (some date)) is to take over.
- "条件检查读取不完整": check the marker directory yourself; do not treat it as having nothing to do.

### Step 2: Continue according to the round record
Read the round record `<资料根>/审计/异常深审/<业务日期>.json` (common rule 3).
- For markers **to take over** (status "深审中（某日）"): look at the round record of **that day**. If it says "执行: 完成" (execution: done) -> only do the wrap-up (step 8), change the remaining markers to "已深审", and **do not re-review the content**. If it is not done -> continue from the "已做" (done so far) of that day's round record, and review the parts not yet done as usual.
- Write the "待审清单" (list to review) into the round record, and do not change it afterwards.

### Step 3: Start work: change markers to "深审中"
For the markers **to review** in this round, change the "状态" (status) to `深审中（<业务日期>）` (deep review in progress (business date)) one by one, using exact replacement. Handle all "待深审" markers before the cutoff point at once, merged into a single deep review; the ones recorded after the cutoff point are left for the next day.

### Step 4: Review
For each marker: read the content in the marker; go back to the original record and verify it (if the marker points to a thread in the Lounge channel, handle it per common rule 9; read the related files, task records and task cards; read Discord with `openclaw message read …`, read-only, written the same way as step 5 of the daily audit); judge whether it is a real problem, how severe it is, and whom it should go to (the original owner of the item, the Controller, the owner). **You only read and draw conclusions; you do not handle anything**: do not change the files under review, do not assign work, do not send messages. If the evidence is insufficient, write "未能核实（原因）" (unable to verify (reason)) and draw no conclusion.

### Step 5: Write the full report
`<资料根>/审计/异常深审/<业务日期>.md` (rewrite the whole file): one section per marker, with the event key, what was seen, what was verified (location of the evidence), the conclusion, the severity, and whom it is recommended to go to.

### Step 6: Write the digest
`<资料根>/审计/异常深审/<业务日期>-摘要.txt`: the first line is `【审计 · 异常深审 · <业务日期>】`; at most 12 lines, at most 1200 characters, plain text; the last line is `完整报告：资料/审计/异常深审/<业务日期>.md` (full report: path).

### Step 7: Change the round record to "执行: 完成"
### Step 8: Only **last**, change the markers to "已深审"
For the markers handled in this round, change the "状态" to `已深审（<业务日期>）` (deep reviewed (business date)) one by one, using exact replacement. **The order is fixed: full report -> digest -> round record "完成" (done) -> markers "已深审" -> call the publish script (common rules 5 and 8) -> final reply.** If interrupted midway, the next run continues according to step 2.
### Step 9: Call the publish script, final reply
Call the publish script per common rules 5 and 8; make the final reply just the one line the script outputs, with nothing else mixed in.
