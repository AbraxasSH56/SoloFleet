### 2 Business date and cutoff point (compute once at the start of the task, write into the round record, never change afterwards)
- One round = task + business date. **Cutoff point = the scheduled time of that business date.** The business date is the local date of "the most recent scheduled time before this run started" (time zone per config `timezone`; `TZN` in the snippet below must be the same). Example: a patrol scheduled at 18:30 is re-run by hand at 09:00 the next day; the most recent 18:30 before that is the previous day, so the business date is the previous day.
- Every later step of the round (reading the increment, file names, report labels) uses the values in the round record and does not recompute from a new "now".
- Use the command below to compute it; do not work it out in your head. First give the two variables of this task (see the "Parameters of this task" section) in front of the command, for example `HM=18:30 DOW= sh -c '<the snippet below>'`; the weekly audit sets DOW to 0 (Sunday), the others leave it empty.

```sh
# business-date-snippet begin
# Usage: set HM (scheduled time such as 18:30, from config jobs.<name>.time) and DOW (only the weekly audit sets it, Sunday is 0; leave empty for daily jobs) before running this snippet.
# TZN on the next code line is the time zone name filled in once at deployment (same as config timezone, e.g. UTC); it is not a variable passed in on each run.
# For tests, FAKE_NOW (seconds) stands in for "now"; do not set it in production.
TZN=<TIMEZONE>
NOW=${FAKE_NOW:-$(date +%s)}
BR() { TZ=$TZN date "$@"; }
D=$(BR -j -f %s "$NOW" +%Y-%m-%d)
for i in 0 1 2 3 4 5 6 7 8; do
  C=$(BR -j -f "%Y-%m-%d %H:%M:%S" "$D $HM:00" +%s)
  W=$(BR -j -f "%Y-%m-%d %H:%M:%S" "$D 12:00:00" +%w)
  if [ "$C" -le "$NOW" ] && { [ -z "$DOW" ] || [ "$W" = "$DOW" ]; }; then break; fi
  D=$(BR -j -v-1d -f "%Y-%m-%d %H:%M:%S" "$D 12:00:00" +%Y-%m-%d)
done
Z=$(BR -j -f %s "$C" +%z)
echo "业务日期=$D 截止点=$(BR -j -f %s "$C" +%Y-%m-%dT%H:%M:%S)${Z%??}:${Z#???}"
# business-date-snippet end
```

### 3 The round record and "half-done"
- Each task has one file per round, `<资料根>/审计/<任务目录>/<业务日期>.json` (task folder / business date), which records only how far the execution got. Format: `{"任务":"…","业务日期":"YYYY-MM-DD","截止点":"…±HH:MM","上一截止点":"…","执行":"进行中|完成","已做":{…},"更新时间":"…"}` (keys: task, business date, cutoff point, previous cutoff point, execution = in progress | done, done-so-far, updated at). The offset in the cutoff point is the real UTC offset of the configured time zone.
- **Read the round record first.** Not there: create it with `执行` set to "进行中" (in progress). `执行: 完成` (done): do not redo the work (do not change the report, the digest or the round record); the patrol, deep review and weekly audit must still call the publish script under common rule 8, and the last reply is only the line the script printed; the daily audit replies with one sentence, "日审 <业务日期> 已完成" (daily audit <business date> completed). `执行` is "进行中": continue from "已做" (done so far); first re-check the current state of steps already done, and do not write or send them twice.
- Whether a report was delivered is not recorded here. The daily audit looks at the official run records. For the patrol, deep review and weekly audit, **the self-publish start business dates** are the three dates in the `EFFECTIVE_FROM` constant of the publish script `publish-self.py` (one each for patrol, deep review and weekly audit; normally the day you turned self-publishing on). Rounds before the start date are judged from the official run records; from the start date on, read the publish receipt `<资料根>/审计/发布/凭据/<任务>-<业务日期>.json` (it is the delivery-status record of the digest, not an account secret, so you may read it). **Trusted delivered** means: the file can be read in full; "任务" and "业务日期" agree with the file name; "账号" is `default`; "频道" is `discord`; "目标" is `channel:<WORKSHOP_CHANNEL_ID>`; "状态" is "已送达"; "消息编号" is a string of 17 to 20 digits; and the file `<任务>-<业务日期>.回执.txt` exists in the same folder. If any one of these fails it is "送达待核" (delivery unverified). If it is trusted-delivered but the "摘要指纹" (digest fingerprint) in the receipt differs from `shasum -a 256` of the current digest file, write "已发摘要与当前文件不同，待核" (the sent digest differs from the current file, to be verified). `ok` or `not-requested` in the official records cannot replace this judgment.

### 5 Command line: read-only commands only
- **Explicitly forbidden**: `openclaw message send` (and any other action that sends, edits or deletes messages), `openclaw models aliases add/remove/set`, `openclaw models set`, `openclaw config set/patch/unset`, `openclaw automations add/edit/run/remove`, `openclaw workboard create/move/dispatch`, `openclaw sessions delete/archive/cleanup`, and any command that changes an alias, configuration, task or task card. - **Allowed read-only commands** (per task, in addition to the ones above): daily audit — `openclaw automations runs/list/show`, `openclaw workboard list/show`, `openclaw audit`, `openclaw message read/thread list/search`, the quota-reading command (see the daily audit instruction), `find`, `jq` (only for reading your own audit files and command output), `git log` (only the usage written below); patrol — `openclaw automations runs/list/show`, `openclaw workboard list/show`, `openclaw message read/thread list/search`, `jq` (only for parsing command output you read and files in `<资料根>`); weekly audit — the daily audit's list (without `git`) plus `openclaw models list/aliases list`; deep review — mainly reading files, plus `openclaw message read/thread list/search` (read Discord when verifying, read-only), `openclaw workboard list/show` (check task cards, read-only), `jq` (only for parsing command output you read and files in `<资料根>`).

## What to do (in order; after finishing each step, update "已做" (done so far) in the round record)

### Step 1: Work out the business date, read the round record
Follow common rules 2 and 3. This round record has two extra fields: "到期提醒已提" (due reminders already raised; a list of item numbers) and "已回写" (written back; true/false). **Increment start** = the `截止点` (cutoff point) of the most recent patrol round record with "执行: 完成" (execution: done); on the very first run there is none, so use the time the task was created.

### Step 2: Read the day's daily audit
- Read `<资料根>/审计/日审/<业务日期>.json` (audit folder "daily audit"): if `执行` (execution) is "完成" (done), read the findings in `<业务日期>.md` and write them into the report section "今天的审计发现" (today's audit findings) (write "无" (none) if there are none). If it is not done or does not exist, write "今日审计未完成" (today's audit not completed), and, from the daily audit's run records (`openclaw automations runs <日审编号> --json --limit 50`; find the ID with `openclaw automations list --all --json` by the name "日审"), write one sentence giving the reason: still running / failed because of quota / errored.
- A daily audit result that arrived late from the previous day (finished only after the patrol started) goes into the section "昨天补完的审计发现" (audit findings completed yesterday), labelled with the business date it actually belongs to.
- **闲聊抽查** (lounge spot-check): the daily audit report has a section "闲聊抽查". **The full report copies that section as it is** (write "无" if there is nothing). **In the digest, add one line only when the count is greater than 0**: "闲聊抽查：N 条疑似，详见日审报告" (lounge spot-check: N suspected, see the daily audit report), naming no one; write nothing when the count is 0. This is not a new message; it is one extra line in the existing digest, and the "at most 12 lines, 1200 characters" limit still applies (if the 12 lines are already used, merge this line into the "今天的审计发现" line). You do not read the Lounge channel yourself.
- **文件对账** (file reconciliation; done by the daily audit's trigger script, you only read the result): in the daily audit `<业务日期>.md`, the "文件对账" line says "新增 N、满 3 天 M、存量 K" (new N, reached 3 days M, existing K). **When N or M is greater than 0**, read `<资料根>/审计/日审/<业务日期>-文件对账.md` directly and take only the entries in the two sections "新增" (new) and "满 3 天" (reached 3 days), one sentence per entry, and put them in the full report after the "异常" (anomalies) section, not in the digest; do not restate "存量". If the file does not exist, or the `业务日期：` (business date) in its header is not this round's, write "文件对账：未能检查（原因）" (file reconciliation: unable to check (reason)) and do not guess entries from the daily audit's one line. If N and M are both 0, write nothing.
- **盲区抽查** (blind-spot check): the daily audit report has the two sections "盲区抽查" and "备份状态" (backup status). The full report copies them as they are; the digest gets one line only when there is a lead, and you add no judgment of your own.

### Step 2 (supplement): Write back the reminder dates in the previous delivered reports (rule: without a real send receipt, never mark an item as reminded)
- The round record has a field "到期提醒已提" (one per business date): write into it the `FOLLOWUPS.md` item numbers that were mentioned in this round's digest. **They cannot be marked at that moment. They count as delivered only once the publish receipt records "已送达" (delivered), so leave them for the next round to write back.**
- What to do in this step: find, among the **most recent few** patrol round records, those where "到期提醒已提" is non-empty and "已回写" is not true. For those whose **digest for that business date is confirmed delivered** (how to decide: for business dates from the patrol start date onward, it must be "trusted as delivered" in the sense of common rule 3, and the digest fingerprint must match the current digest file; for business dates before the start date, still go by the patrol's own run records, where that business date has one run with `deliveryStatus` equal to `delivered`; read the run records page by page with `openclaw automations runs <巡查编号> --json --limit 50 --offset <n>`), use an exact replacement to change the `lastMentionedDate` of those items to that report's business date (change only this one field, do not touch anything else), read it back to confirm, and then change that round record's "已回写" to true. Do **not** change anything where there is no publish receipt, delivery is unverified, or the digest that was sent differs from the current file (before the start date: `not-delivered`, `unknown`, or no run record found); look again next round. The publish receipt is read-only: do not edit or delete it. As a result the reminder will appear again the next day; this is intended.
- If the exact replacement cannot find the original text (`FOLLOWUPS.md` was changed by someone else), do not force the edit; write "提醒日期未回写（文件已被改动）" (reminder date not written back (file has been changed)) into the round record and the report.
