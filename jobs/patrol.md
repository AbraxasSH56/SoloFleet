### 2 Business date and cutoff point (compute once at the start of the task, write into the round record, never change afterwards)
- One round = task + business date. **Cutoff point = the scheduled time of that business date.** The business date is the local date of "the most recent scheduled time before this run started" (time zone per config `timezone`; `TZN` in the snippet below must be the same). Example: a patrol scheduled at 18:30 is re-run by hand at 09:00 the next day; the most recent 18:30 before that is the previous day, so the business date is the previous day.
- Every later step of the round (reading the increment, file names, report labels) uses the values in the round record and does not recompute from a new "now".
- Use the command below to compute it; do not work it out in your head. First give the two variables of this task (see the "Parameters of this task" section) in front of the command, for example `HM=18:30 DOW= sh -c '<the snippet below>'`; the weekly audit sets DOW to 0 (Sunday), the others leave it empty. The snippet prints one line with the business date and the cutoff point; the two labels in that line are `business_date=` and `cutoff=`. Read the two values after the labels.

```sh
# business-date-snippet begin
# Usage: set HM (scheduled time such as 18:30, from config jobs.<name>.time) and DOW (only the weekly audit sets it, Sunday is 0; leave empty for daily jobs) before running this snippet.
# TZN on the next code line is the time zone name filled in once at deployment (same as config timezone, e.g. UTC); it is not a variable passed in on each run.
# For tests, FAKE_NOW (seconds) stands in for "now"; do not set it in production.
TZN=<TIMEZONE>
NOW=${FAKE_NOW:-$(date +%s)}
BR() { TZ=$TZN date "$@"; }
D=$(BR -j -f %s "$NOW" +%Y-%m-%d)
for i in 0 1 2 3 4 5 6 7 8; do
  C=$(BR -j -f "%Y-%m-%d %H:%M:%S" "$D $HM:00" +%s)
  W=$(BR -j -f "%Y-%m-%d %H:%M:%S" "$D 12:00:00" +%w)
  if [ "$C" -le "$NOW" ] && { [ -z "$DOW" ] || [ "$W" = "$DOW" ]; }; then break; fi
  D=$(BR -j -v-1d -f "%Y-%m-%d %H:%M:%S" "$D 12:00:00" +%Y-%m-%d)
done
Z=$(BR -j -f %s "$C" +%z)
echo "business_date=$D cutoff=$(BR -j -f %s "$C" +%Y-%m-%dT%H:%M:%S)${Z%??}:${Z#???}"
# business-date-snippet end
```

### 3 The round record and "half-done"
- Each task has one file per round, `<DATA_ROOT>/audit/<TASK_FOLDER>/<BUSINESS_DATE>.json`, which records only how far the execution got. Format: `{"task":"…","business_date":"YYYY-MM-DD","cutoff":"…±HH:MM","previous_cutoff":"…","execution":"in-progress|done","done":{…},"updated_at":"…"}`. The offset in `cutoff` is the real UTC offset of the configured time zone.
- **Read the round record first.** Not there: create it with `execution` set to "in-progress". `execution: done`: do not redo the work (do not change the report, the digest or the round record); the patrol, deep review and weekly audit must still call the publish script under common rule 8, and the last reply is only the line the script printed; the daily audit replies with one sentence, "daily-audit <BUSINESS_DATE> finished". `execution` is "in-progress": continue from `done`; first re-check the current state of steps already done, and do not write or send them twice.
- Whether a report was delivered is not recorded here. The daily audit looks at the official run records. For the patrol, deep review and weekly audit, **the self-publish start business dates** are the three dates in the `EFFECTIVE_FROM` constant of the publish script `publish-self.py` (one each for patrol, deep review and weekly audit; normally the day you turned self-publishing on). Rounds before the start date are judged from the official run records; from the start date on, read the publish receipt `<DATA_ROOT>/audit/publish/receipts/<task>-<BUSINESS_DATE>.json` (it is the delivery-status record of the digest, not an account secret, so you may read it). **Trusted delivered** means: the file can be read in full; `task` and `business_date` agree with the file name; `account` is `default`; `channel` is `discord`; `target` is `channel:<WORKSHOP_CHANNEL_ID>`; `state` is "delivered"; `message_id` is a string of 17 to 20 digits; and the file `<task>-<BUSINESS_DATE>.receipt.txt` exists in the same folder. If any one of these fails it is "delivery-to-verify". If it is trusted-delivered but the `digest` in the receipt differs from `shasum -a 256` of the current digest file, write "the sent digest differs from the current file, to be verified". `ok` or `not-requested` in the official records cannot replace this judgment.

### 5 Command line: read-only commands only

## What to do (in order; after finishing each step, update `done` in the round record)

### Step 1: Work out the business date, read the round record
Follow common rules 2 and 3. This round record has two extra fields: `reminders_marked` (due reminders already raised; a list of item numbers) and `written_back` (true/false). **Increment start** = the `cutoff` of the most recent patrol round record with `execution: done`; on the very first run there is none, so use the time the task was created.

### Step 2: Read the day's daily audit
- Read `<DATA_ROOT>/audit/daily/<BUSINESS_DATE>.json` (audit folder "daily audit"): if `execution` is "done", read the findings in `<BUSINESS_DATE>.md` and write them into the report section "Today's audit findings" (write "None" if there are none). If it is not done or does not exist, write "Today's audit not completed", and, from the daily audit's run records (`openclaw automations runs <daily-audit ID> --json --limit 50`; find the ID with `openclaw automations list --all --json` by the name "daily-audit"), write one sentence giving the reason: still running / failed because of quota / errored.
- A daily audit result that arrived late from the previous day (finished only after the patrol started) goes into the section "Audit findings completed yesterday", labelled with the business date it actually belongs to.
- **Lounge spot-check**: the daily audit report has a section "Lounge spot-check". **The full report copies that section as it is** (write "None" if there is nothing). **In the digest, add one line only when the count is greater than 0**: "Lounge spot-check: N suspected, see the daily audit report", naming no one; write nothing when the count is 0. This is not a new message; it is one extra line in the existing digest, and the "at most 12 lines, 1200 characters" limit still applies (if the 12 lines are already used, merge this line into the "Today's audit findings" line). You do not read the Lounge channel yourself.
- **File reconcile** (done by the daily audit's trigger script, you only read the result): in the daily audit `<BUSINESS_DATE>.md`, the "File reconcile" line says "File reconcile: new N, day 3 M, existing K". **When N or M is greater than 0**, read `<DATA_ROOT>/audit/daily/<BUSINESS_DATE>-file-reconcile.md` directly and take only the entries in the two sections "New" and "Day 3", one sentence per entry, and put them in the full report after the "Anomalies" section, not in the digest; do not restate "existing". If the file does not exist, or the `Business date:` in its header is not this round's, write "File reconcile: could not check (reason)" and do not guess entries from the daily audit's one line. If N and M are both 0, write nothing.
- **Blind-spot check**: the daily audit report has the two sections "Blind-spot check" and "Backup status". The full report copies them as they are; the digest gets one line only when there is a lead, and you add no judgment of your own.

### Step 2 (supplement): Write back the reminder dates in the previous delivered reports (rule: without a real send receipt, never mark an item as reminded)
- The round record has a field `reminders_marked` (one per business date): write into it the `FOLLOWUPS.md` item numbers that were mentioned in this round's digest. **They cannot be marked at that moment. They count as delivered only once the publish receipt records "delivered", so leave them for the next round to write back.**
- What to do in this step: find, among the **most recent few** patrol round records, those where `reminders_marked` is non-empty and `written_back` is not true. For those whose **digest for that business date is confirmed delivered** (how to decide: for business dates from the patrol start date onward, it must be "trusted as delivered" in the sense of common rule 3, and the digest fingerprint must match the current digest file; for business dates before the start date, still go by the patrol's own run records, where that business date has one run with `deliveryStatus` equal to `delivered`; read the run records page by page with `openclaw automations runs <patrol ID> --json --limit 50 --offset <n>`), use an exact replacement to change the `lastMentionedDate` of those items to that report's business date (change only this one field, do not touch anything else), read it back to confirm, and then change that round record's `written_back` to true. Do **not** change anything where there is no publish receipt, delivery is unverified, or the digest that was sent differs from the current file (before the start date: `not-delivered`, `unknown`, or no run record found); look again next round. The publish receipt is read-only: do not edit or delete it. As a result the reminder will appear again the next day; this is intended.
- If the exact replacement cannot find the original text (`FOLLOWUPS.md` was changed by someone else), do not force the edit; write "Reminder date not written back (the file has been changed)" into the round record and the report.
- This is the only place where the patrol may write a file outside `<DATA_ROOT>` (stated in items 1 and 4 of the common block).

### Step 3: Read the material for the increment, for "matters waiting for the owner's decision" and for "due reminders"
- Read the thread progress sentences that changed within the increment range, plus the project entries and the task records (`<DATA_ROOT>/projects/*/tasks/`), specifically the two sections "Current status" and "Waiting for the owner's decision"; also old items that were reopened, cited, or requested by the owner. Progress sentences and the "Status:" line are sorted by their opening words: those opening with "Did not run" or "Stuck" get one sentence each (which project, where it is stuck, since which day) and go into the full report after the "Anomalies" section; the digest only gets one line "N did not run, M stuck" (omit the line if there are none). "Waiting for your decision" is not judged by status alone: whenever the "Waiting for the owner's decision" section is still open, whatever the status says, it goes under "Matters waiting for your decision" below. For projects with activity, state who it was assigned to, who was brought in later, and how far it has got (sources: the task record's "Current status", thread progress sentences; `openclaw workboard list/show`), and write this into the full report section "Projects with activity today". **The report mentions only projects with activity that day; a project with no activity does not appear, or is counted as a single number; a project with a new blocker or a new decision does appear, even if it has no due reminder.**
- **Due reminders (daily follow-up)**: read `<PROJECT_ROOT>/runtime/controller/FOLLOWUPS.md` (it contains one JSON list; the fields include `id`, `reason`, `nextReview`, `status`, `withoutDeadline`, `lastMentionedDate`, `firstStep`, `estimatedEffortBudget`, `workboardCardId` and others). An item is due only if its `status` is `active` and its `nextReview` is not later than this round's cutoff date (paused, stopped and archived items do not count).
