### 2 Business date and cutoff point (compute once at the start of the task, write into the round record, never change afterwards)
- One round = task + business date. **Cutoff point = the scheduled time of that business date.** The business date is the local date of "the most recent scheduled time before this run started" (time zone per config `timezone`; `TZN` in the snippet below must be the same). Example: a patrol scheduled at 18:30 is re-run by hand at 09:00 the next day; the most recent 18:30 before that is the previous day, so the business date is the previous day.
- Every later step of the round (reading the increment, file names, report labels) uses the values in the round record and does not recompute from a new "now".
- Use the command below to compute it; do not work it out in your head. First give the two variables of this task (see the "Parameters of this task" section) in front of the command, for example `HM=18:30 DOW= sh -c '<the snippet below>'`; the weekly audit sets DOW to 0 (Sunday), the others leave it empty. The snippet prints one line with the business date and the cutoff point; the two labels in that line are `business_date=` and `cutoff=`. Read the two values after the labels.

```sh
# business-date-snippet begin
# Usage: set HM (scheduled time such as 18:30, from config jobs.<name>.time) and DOW (only the weekly audit sets it, Sunday is 0; leave empty for daily jobs) before running this snippet.
# TZN on the next code line is the time zone name filled in once at deployment (same as config timezone, e.g. UTC); it is not a variable passed in on each run.
# For tests, FAKE_NOW (seconds) stands in for "now"; do not set it in production.
TZN=<TIMEZONE>
NOW=${FAKE_NOW:-$(date +%s)}
BR() { TZ=$TZN date "$@"; }
D=$(BR -j -f %s "$NOW" +%Y-%m-%d)
for i in 0 1 2 3 4 5 6 7 8; do
  C=$(BR -j -f "%Y-%m-%d %H:%M:%S" "$D $HM:00" +%s)
  W=$(BR -j -f "%Y-%m-%d %H:%M:%S" "$D 12:00:00" +%w)
  if [ "$C" -le "$NOW" ] && { [ -z "$DOW" ] || [ "$W" = "$DOW" ]; }; then break; fi
  D=$(BR -j -v-1d -f "%Y-%m-%d %H:%M:%S" "$D 12:00:00" +%Y-%m-%d)
done
Z=$(BR -j -f %s "$C" +%z)
echo "business_date=$D cutoff=$(BR -j -f %s "$C" +%Y-%m-%dT%H:%M:%S)${Z%??}:${Z#???}"
# business-date-snippet end
```

### 3 The round record and "half-done"
- Each task has one file per round, `<DATA_ROOT>/audit/<TASK_FOLDER>/<BUSINESS_DATE>.json`, which records only how far the execution got. Format: `{"task":"…","business_date":"YYYY-MM-DD","cutoff":"…±HH:MM","previous_cutoff":"…","execution":"in-progress|done","done":{…},"updated_at":"…"}`. The offset in `cutoff` is the real UTC offset of the configured time zone.
- **Read the round record first.** Not there: create it with `execution` set to "in-progress". `execution: done`: do not redo the work (do not change the report, the digest or the round record); the patrol, deep review and weekly audit must still call the publish script under common rule 8, and the last reply is only the line the script printed; the daily audit replies with one sentence, "daily-audit <BUSINESS_DATE> finished". `execution` is "in-progress": continue from `done`; first re-check the current state of steps already done, and do not write or send them twice.
- Whether a report was delivered is not recorded here. The daily audit looks at the official run records. For the patrol, deep review and weekly audit, **the self-publish start business dates** are the three dates in the `EFFECTIVE_FROM` constant of the publish script `publish-self.py` (one each for patrol, deep review and weekly audit; normally the day you turned self-publishing on). Rounds before the start date are judged from the official run records; from the start date on, read the publish receipt `<DATA_ROOT>/audit/publish/receipts/<task>-<BUSINESS_DATE>.json` (it is the delivery-status record of the digest, not an account secret, so you may read it). **Trusted delivered** means: the file can be read in full; `task` and `business_date` agree with the file name; `account` is `default`; `channel` is `discord`; `target` is `channel:<WORKSHOP_CHANNEL_ID>`; `state` is "delivered"; `message_id` is a string of 17 to 20 digits; and the file `<task>-<BUSINESS_DATE>.receipt.txt` exists in the same folder. If any one of these fails it is "delivery-to-verify". If it is trusted-delivered but the `digest` in the receipt differs from `shasum -a 256` of the current digest file, write "the sent digest differs from the current file, to be verified". `ok` or `not-requested` in the official records cannot replace this judgment.

### 5 Command line: read-only commands only

## What to do (in order; after each step, update the `done` field of the round record)

### Step 1: Work out the business date and read the round record
Follow common rules 2 and 3. **Increment start** = the `cutoff` of the most recent round record in `<DATA_ROOT>/audit/daily/` that has `execution: done`; if there is none, take 24 hours before the cutoff point. Write the start into the `increment_start` field of the round record.

### Step 2: Read the command spot-check file (the trigger script does the command spot-check; you only read the result)
- Before the daily audit starts, the task's trigger script has already finished the command spot-check for every role (including the Desktop operator, and the patrol, daily audit, anomaly deep review and weekly audit roles that go through the API route), and written it to `<DATA_ROOT>/audit/daily/<BUSINESS_DATE>-command-check.md`. **You only read this file**; do not look for or read any session records yourself, and do not sample commands yourself. All of the Desktop operator's commands are listed; those that hit a screen-action keyword are marked ⚠ and put in the section "Keyword hits"; record an anomaly marker for them per rule 5 item ③. Those marked "not on the whitelist" are only leads; do not record a marker for them.
- The file has three sections: "Count reconciliation", "Keyword hits", "All commands". Write every item under keyword hits into the findings (role, time, matched word, command fragment) and record an anomaly marker (rule 5, see Step 5). For a role whose reconciliation result is "records insufficient", write it into the findings as is; do not treat it as fine.
- **The file does not exist, or the business date in the file header is not this round's** -> write in the findings: "Command spot-check: records insufficient (the script did not generate it; the task may have been forced to run manually, skipping the trigger script)". **Do not read session records because of this.**
- Only when every role in the file is "no command-line calls this round", write "Command spot-check: no command-line calls this round".

### Step 3: Read the increment
Read what changed within the increment range: task records (`<DATA_ROOT>/projects/*/tasks/`), the project entry `PROJECT.md`, progress sentences; old items that were reopened or are referenced by the current task; the existing markers in `audit/anomaly-flags/` (check the event key and `seen_again`). By default read the condensed progress and anomalies; when an item looks abnormal, you may go back to the raw records. Do not read items that are finished, archived, or untouched since the previous round.

### Step 4: Document maintenance (fix only typos, broken links and formatting that can be determined uniquely)
- Before fixing: for each spot, first record a line `{file, original, new, status:"about-to-change"}` under `changes` in the round record; make the change with exact replacement; read it back to confirm the new text is there and the original text is not, then change the status to "confirmed".
- **On a redo**, for every line still "about-to-change", look at the file's current state: new text present, original absent -> already changed, record "confirmed"; original still present -> change it again; neither present -> someone else changed it, record "Not fixed: the file was changed; handed to its original owner" and write it into the findings.
- Outdated entries, and status and decision issues: do not change them yourself; write them into the findings, naming the original owner (worker bot, lead bot, or the Controller).
- Do not touch `INDEX.md`, patrol files, status, decisions, ledgers, `owner-status.md`, or task cards.

### Step 5: Immediate-trigger items (rough check; only leads, to be verified by the deep review)
When you find one, create a new file in `<DATA_ROOT>/audit/anomaly-flags/`. If the same thing is seen again, only add a line to `seen_again` in the existing file using exact replacement, leaving the status unchanged; create a new file only when the same object has a new event, with a different fingerprint. **Always read Discord through the command line, read-only, with account `default`; never use `send`**: `openclaw message read --channel discord --account default --target channel:<channel or thread ID> --limit 100 --json`. The output of this command may be preceded by non-JSON warning lines: append `2>&1 | sed -n '/^{/,$p'` to the command, which takes everything from the first line starting with `{` to the end, whether or not the warning is there, then pipe into `jq` to parse; do not use `tail -n +<number>` or `jq -R`. Filter the window yourself by message time; if one page is not enough, page backwards with `--before <ID of the earliest message>` until you are earlier than the window start. For threads, first list them with `openclaw message thread list --channel discord --account default --guild-id <server ID>` and then read them one by one. To look up by bot, you can use `openclaw message search … --author-id <user ID>`.

### Step 6: Quota reading and quota anomaly
- Reading command (optional: first install the CodexBar command line and put its path in the CodexBar path entry under `paths` in the config; if it is not installed or cannot be read, write "unknown" for the whole step, and do not trigger that day): `<CODEXBAR_BIN> usage --provider claude --source cli --format json --no-credits`. Write "this week's used percentage" and "this week's reset time" into `<DATA_ROOT>/audit/quota-readings/<BUSINESS_DATE>.json`: `{"business_date","read_at","source":"queried|reused-sample|unknown","sampled_at","week_used_percent","week_reset_time","valid_increment":number or null,"not_counted_reason":"reset-day|unknown|regression|interval-under-12h|interval-over-36h|sample-too-old|none","task_count","api_quota_left":"not-connected"}` (keys, in order: business date, read time, source, sample time, this week's used percentage, this week's reset time, valid increment (a number or null), reason not counted, task count of the day, remaining API credit "not connected"). `source`: write "queried" if the command returned it this time; write "reused-sample" if what was returned is a cached result with a sample time; write "unknown" if it cannot be read.
- **Daily increment** = today's reading minus the previous valid reading. In these cases the day has no valid increment and does not trigger: the two readings are not in the same weekly window (different reset times; record "reset-day"); the reading is "unknown"; the reading is lower than the previous one (regression, "regression"); the two readings are less than 12 hours or more than 36 hours apart ("interval-under-12h", "interval-over-36h"); for a "reused-sample" reading, the sample time is more than 1 hour before the daily audit started ("sample-too-old"). If the interval is between 12 and 36 hours, convert it as 24 hours.
- **Baseline** = the average of the valid increments in the most recent 7 calendar days **before** today (today not included; increments may come from different weekly windows). With fewer than 4 valid increments, only list that day's consumption in the findings, and do not trigger.
- **Task count** = the number of task cards "completed" that day + the number of task cards "advanced" that day; a card updated several times in one day counts as 1; a card both completed and advanced counts as 1.
- **Trigger condition**: today's valid increment > 2 times the baseline, **and** today's task count is below "half of the quota multiple" times the average daily task count over the last 7 days (for example, if the quota was used at 3 times, the task count is below 1.5 times). When the 7-day daily average task count is 0, only a task count of 0 today counts as "no corresponding increase". When triggered, record an anomaly marker (rule 6). **Only an investigation lead**: other uses of the same account, such as development sessions, are included in it as well; do not use it to conclude that any bot violated a rule.
- Worked examples (calculate exactly like this, do not skip steps in your head; "quota multiple" = today's increment / baseline):
  - **Trigger**: baseline 4%, today's increment 12% (3 times, more than 2 times); average daily task count over the last 7 days is 6, so the task-count threshold = 6 x 3 / 2 = 9; today's task count is 2, less than 9 -> trigger.
  - **No trigger (workload kept up)**: same baseline 4%, increment 12%, threshold 9; today's task count is 10, not less than 9 -> no trigger.
  - **No trigger (did not exceed 2 times)**: baseline 4%, today's increment 6% (1.5 times) -> no trigger.
  - **Only list (not enough samples)**: only 3 valid increments in the last 7 days, today's increment is 20% -> only list that day's consumption in the findings, no trigger.
