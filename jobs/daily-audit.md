> These rules are used together with their Chinese literals unchanged, because the programs still match Chinese literals. In the text, all-caps placeholders in angle brackets (such as `<GUILD_ID>`, `<TIMEZONE>`, `<WORKSHOP_CHANNEL_ID>`) are filled in once at deployment; Chinese placeholders such as `<资料根>` (data root) and `<项目根>` (project root) are taken from the task message on every run, so do not replace them. See `jobs/README.md` for details.

This task uses the API credit that comes with a subscription (if your subscription plan includes it). When it is used up, stop; do not switch back to the subscription. For how to write the provider, see `config/examples/api-credit-providers.example.json`.

When you write down "where a manual run of a scheduled task was delivered" (which channel), you must read **that run's own delivery record** (the `delivery` of that run in `cron runs`) or the message in the channel itself. The task's **current** delivery setting only applies to the future; do not use it to infer what happened in the past. If you cannot read it, write "投递位置未核实" (delivery location unverified).

Applicable role: `system-auditor`. **Do not deliver and do not send any message**: the official failure alert is the only thing that may appear from the Workshop channel.

  - Channel list: the "Discord 频道" (Discord channel) column of `<资料根>/INDEX.md`, one line per project

### 2 Business date and cutoff point (compute once at the start of the task, write into the round record, never change afterwards)
- One round = task + business date. **Cutoff point = the scheduled time of that business date.** The business date is the local date of "the most recent scheduled time before this run started" (time zone per config `timezone`; `TZN` in the snippet below must be the same). Example: a patrol scheduled at 18:30 is re-run by hand at 09:00 the next day; the most recent 18:30 before that is the previous day, so the business date is the previous day.
- Every later step of the round (reading the increment, file names, report labels) uses the values in the round record and does not recompute from a new "now".
- Use the command below to compute it; do not work it out in your head. First give the two variables of this task (see the "Parameters of this task" section) in front of the command, for example `HM=18:30 DOW= sh -c '<the snippet below>'`; the weekly audit sets DOW to 0 (Sunday), the others leave it empty.

```sh
# business-date-snippet begin
# Usage: set HM (scheduled time such as 18:30, from config jobs.<name>.time) and DOW (only the weekly audit sets it, Sunday is 0; leave empty for daily jobs) before running this snippet.
# TZN on the next code line is the time zone name filled in once at deployment (same as config timezone, e.g. UTC); it is not a variable passed in on each run.
# For tests, FAKE_NOW (seconds) stands in for "now"; do not set it in production.
TZN=<TIMEZONE>
NOW=${FAKE_NOW:-$(date +%s)}
BR() { TZ=$TZN date "$@"; }
D=$(BR -j -f %s "$NOW" +%Y-%m-%d)
for i in 0 1 2 3 4 5 6 7 8; do
  C=$(BR -j -f "%Y-%m-%d %H:%M:%S" "$D $HM:00" +%s)
  W=$(BR -j -f "%Y-%m-%d %H:%M:%S" "$D 12:00:00" +%w)
  if [ "$C" -le "$NOW" ] && { [ -z "$DOW" ] || [ "$W" = "$DOW" ]; }; then break; fi
  D=$(BR -j -v-1d -f "%Y-%m-%d %H:%M:%S" "$D 12:00:00" +%Y-%m-%d)
done
Z=$(BR -j -f %s "$C" +%z)
echo "业务日期=$D 截止点=$(BR -j -f %s "$C" +%Y-%m-%dT%H:%M:%S)${Z%??}:${Z#???}"
# business-date-snippet end
```

### 3 The round record and "half-done"
- Each task has one file per round, `<资料根>/审计/<任务目录>/<业务日期>.json` (task folder / business date), which records only how far the execution got. Format: `{"任务":"…","业务日期":"YYYY-MM-DD","截止点":"…±HH:MM","上一截止点":"…","执行":"进行中|完成","已做":{…},"更新时间":"…"}` (keys: task, business date, cutoff point, previous cutoff point, execution = in progress | done, done-so-far, updated at). The offset in the cutoff point is the real UTC offset of the configured time zone.
- **Read the round record first.** Not there: create it with `执行` set to "进行中" (in progress). `执行: 完成` (done): do not redo the work (do not change the report, the digest or the round record); the patrol, deep review and weekly audit must still call the publish script under common rule 8, and the last reply is only the line the script printed; the daily audit replies with one sentence, "日审 <业务日期> 已完成" (daily audit <business date> completed). `执行` is "进行中": continue from "已做" (done so far); first re-check the current state of steps already done, and do not write or send them twice.
- Whether a report was delivered is not recorded here. The daily audit looks at the official run records. For the patrol, deep review and weekly audit, **the self-publish start business dates** are the three dates in the `EFFECTIVE_FROM` constant of the publish script `publish-self.py` (one each for patrol, deep review and weekly audit; normally the day you turned self-publishing on). Rounds before the start date are judged from the official run records; from the start date on, read the publish receipt `<资料根>/审计/发布/凭据/<任务>-<业务日期>.json` (it is the delivery-status record of the digest, not an account secret, so you may read it). **Trusted delivered** means: the file can be read in full; "任务" and "业务日期" agree with the file name; "账号" is `default`; "频道" is `discord`; "目标" is `channel:<WORKSHOP_CHANNEL_ID>`; "状态" is "已送达"; "消息编号" is a string of 17 to 20 digits; and the file `<任务>-<业务日期>.回执.txt` exists in the same folder. If any one of these fails it is "送达待核" (delivery unverified). If it is trusted-delivered but the "摘要指纹" (digest fingerprint) in the receipt differs from `shasum -a 256` of the current digest file, write "已发摘要与当前文件不同，待核" (the sent digest differs from the current file, to be verified). `ok` or `not-requested` in the official records cannot replace this judgment.

### 5 Command line: read-only commands only
- **Explicitly forbidden**: `openclaw message send` (and any other action that sends, edits or deletes messages), `openclaw models aliases add/remove/set`, `openclaw models set`, `openclaw config set/patch/unset`, `openclaw automations add/edit/run/remove`, `openclaw workboard create/move/dispatch`, `openclaw sessions delete/archive/cleanup`, and any command that changes an alias, configuration, task or task card. - **Basic read-only commands every task may use**: `ls`, `cat`, `grep`, `sort`, `sed` (without `-i`), `comm`, `wc`, `head`, `tail`, `cd`, `date`, `shasum`.
- **Allowed read-only commands** (per task, in addition to the ones above): daily audit — `openclaw automations runs/list/show`, `openclaw workboard list/show`, `openclaw audit`, `openclaw message read/thread list/search`, the quota-reading command (see the daily audit instruction), `find`, `jq` (only for reading your own audit files and command output), `git log` (only the usage written below); patrol — `openclaw automations runs/list/show`, `openclaw workboard list/show`, `openclaw message read/thread list/search`, `jq` (only for parsing command output you read and files in `<资料根>`); weekly audit — the daily audit's list (without `git`) plus `openclaw models list/aliases list`; deep review — mainly reading files, plus `openclaw message read/thread list/search` (read Discord when verifying, read-only), `openclaw workboard list/show` (check task cards, read-only), `jq` (only for parsing command output you read and files in `<资料根>`).
- **Limits on `jq` and `git`**: `jq` is only for parsing; do not use `-f`, `--rawfile`, `--slurpfile`, `-R`, `-n`; always wrap the filter in **single quotes** (a `$` inside double quotes is blocked by the guard); write Chinese key names as `.["键名"]` (jq 1.7 gives a syntax error for `.角色`; use the bracket form); do not write words from the guard's forbidden list in a filter (the guard decides; at least `env`, `ENV`, `$__loc__`, `input_filename`, `input`, `inputs`, `import`, `include`, `debug`, `stderr`, `halt`, `halt_error`; these words are blocked even inside field names or strings); do not save the result to disk. The patrol's `jq` limits exist only at this instruction level. Commit time and commit message are only leads: you must never conclude "who changed it" from them alone, and when you put them in a finding, still mark it "只作线索" (lead only).
- **Forms that are often blocked**: to see a file's modification time use `ls -lT path` (macOS `ls` has no `--time-style`); to limit `grep` output use `-m number`, not `--max-count`; parentheses in `find` are written `\(` and `\)` (with a backslash); to learn how a command is used, do not add `--help` to openclaw commands: the instructions already give the forms you may use; call multiple commands one by one, do not chain them with `;`, `&&` or `||` (the fixed snippets are run whole and verbatim under common rule 5 and are not affected by this sentence; do not split them).

Your own report, digest and round record are changed only by rewriting them whole; get wording such as forms of address right when generating them. Do not read or scan the board's database files (`.sqlite` etc.) directly; read task cards only with the `workboard` commands listed for you, and if none is listed write "未能核实：任务卡（没有读取命令）" (unable to verify: task cards, no read command). For a step the existing commands cannot do, write "未能检查：<what>（reason）" (unable to check: …) as in rule 7 and do not invent another way. "Could not read" and "did not happen" are written separately in reports: never write something you could not read as "0 times" or "none". **Fixed-snippet exception**: only these are allowed — the complete business-date snippet of common rule 2 with its specified `sh -c` form (where it applies to your task); the complete "out-of-scope file check" snippet that daily audit step 5 and weekly audit step 4 run by reference; and the complete "weekly program check" snippet of weekly audit step 2 (for that step only, with no variables, verbatim as `sh -c '<snippet text>'`, with no command before or after). The command-list limits in this rule govern only commands run in `exec` and similar command tools; file reading, whole-file writing, `message`, `edit`/`Edit`, `web_fetch` and the like are still used only as this file allows for your task (purpose, target, way of writing, no changes after completion), and the other prohibitions of this rule apply to all tools: changing tools does not loosen them.

## What to do (in order; after each step, update the "已做" (done) field of the round record)

### Step 1: Work out the business date and read the round record
Follow common rules 2 and 3. **Increment start** = the `截止点` (cutoff point) of the most recent round record in `<资料根>/审计/日审/` that has "执行: 完成" (execution: complete); if there is none, take 24 hours before the cutoff point. Write the start into the "增量起点" (increment start) field of the round record.

### Step 2: Read the command spot-check file (the trigger script does the command spot-check; you only read the result)
- Before the daily audit starts, the task's trigger script has already finished the command spot-check for every role (including the Desktop operator, and the patrol, daily audit, anomaly deep review and weekly audit roles that go through the API route), and written it to `<资料根>/审计/日审/<业务日期>-命令抽查.md`. **You only read this file**; do not look for or read any session records yourself, and do not sample commands yourself. All of the Desktop operator's commands are listed; those that hit a screen-action keyword are marked ⚠ and put in the section "命中关键字" (keyword hits); record an anomaly marker for them per rule 5 item ③. Those marked "非白名单" (not on the whitelist) are only leads; do not record a marker for them.
- The file has three sections: "条数对账" (count reconciliation), "命中关键字" (keyword hits), "全部命令" (all commands). Write every item under keyword hits into the findings (role, time, matched word, command fragment) and record an anomaly marker (rule 5, see Step 5). For a role whose reconciliation result is "记录不足" (records insufficient), write it into the findings as is; do not treat it as fine.
- **The file does not exist, or the business date in the file header is not this round's** -> write in the findings: "命令抽查：记录不足（脚本没有生成，可能是任务被强制手动运行、跳过了触发脚本）" (command spot-check: records insufficient (the script did not generate it; the task may have been forced to run manually, skipping the trigger script)). **Do not read session records because of this.**
- Only when every role in the file is "本轮没有命令行调用" (no command-line calls this round), write "命令抽查：本轮没有命令行调用" (command spot-check: no command-line calls this round).

### Step 3: Read the increment
Read what changed within the increment range: task records (`<资料根>/项目/*/任务/`), the project entry `PROJECT.md`, progress sentences; old items that were reopened or are referenced by the current task; the existing markers in `审计/异常标记/` (anomaly markers folder) (check the event key and "再次发现" (seen again)). By default read the condensed progress and anomalies; when an item looks abnormal, you may go back to the raw records. Do not read items that are finished, archived, or untouched since the previous round.

### Step 4: Document maintenance (fix only typos, broken links and formatting that can be determined uniquely)
- Before fixing: for each spot, first record a line `{文件, 原文, 新文字, 状态:"准备改"}` (file, original text, new text, status: "about to change") under "修改" (changes) in the round record; make the change with exact replacement; read it back to confirm the new text is there and the original text is not, then change the status to "已确认" (confirmed).
- **On a redo**, for every line still "准备改", look at the file's current state: new text present, original absent -> already changed, record "已确认"; original still present -> change it again; neither present -> someone else changed it, record "未修，文件已被改动，交原责任者" (not fixed, the file was changed by someone else, handed to the original owner) and write it into the findings.
- Outdated entries, and status and decision issues: do not change them yourself; write them into the findings, naming the original owner (worker bot, lead bot, or the Controller).
- Do not touch `INDEX.md`, patrol files, status, decisions, ledgers, `主人现况.md` (owner's current situation), or task cards.

### Step 5: Immediate-trigger items (rough check; only leads, to be verified by the deep review)

### Step 6: Quota reading and quota anomaly
- Reading command (optional: first install the CodexBar command line and put its path in the CodexBar path entry under `paths` in the config; if it is not installed or cannot be read, write "未知" (unknown) for the whole step, and do not trigger that day): `<CODEXBAR_BIN> usage --provider claude --source cli --format json --no-credits`. Write "this week's used percentage" and "this week's reset time" into `<资料根>/审计/额度读数/<业务日期>.json` (quota readings folder): `{"业务日期","读取时间","来源":"刚查询|复用采样|未知","采样时间","本周已用百分比","本周重置时间","有效增量":数字或null,"不计原因":"重置日|未知|倒退|间隔不足12小时|间隔超过36小时|采样过旧|无","当天任务数","API额度剩余":"未接入"}` (keys, in order: business date, read time, source, sample time, this week's used percentage, this week's reset time, valid increment (a number or null), reason not counted, task count of the day, remaining API credit "not connected"). `来源` (source): write "刚查询" (just queried) if the command returned it this time; write "复用采样" (reused sample) if what was returned is a cached result with a sample time; write "未知" (unknown) if it cannot be read.
- **Daily increment** = today's reading minus the previous valid reading. In these cases the day has no valid increment and does not trigger: the two readings are not in the same weekly window (different reset times; record "重置日" (reset day)); the reading is "未知"; the reading is lower than the previous one (regression, "倒退"); the two readings are less than 12 hours or more than 36 hours apart; for a "复用采样" reading, the sample time is more than 1 hour before the daily audit started. If the interval is between 12 and 36 hours, convert it as 24 hours.
- **Baseline** = the average of the valid increments in the most recent 7 calendar days **before** today (today not included; increments may come from different weekly windows). With fewer than 4 valid increments, only list that day's consumption in the findings, and do not trigger.
- **Task count** = the number of task cards "完成" (completed) that day + the number of task cards "推进" (advanced) that day; a card updated several times in one day counts as 1; a card both completed and advanced counts as 1.
- **Trigger condition**: today's valid increment > 2 times the baseline, **and** today's task count is below "half of the quota multiple" times the average daily task count over the last 7 days (for example, if the quota was used at 3 times, the task count is below 1.5 times). When the 7-day daily average task count is 0, only a task count of 0 today counts as "no corresponding increase". When triggered, record an anomaly marker (rule 6). **Only an investigation lead**: other uses of the same account, such as development sessions, are included in it as well; do not use it to conclude that any bot violated a rule.
- Worked examples (calculate exactly like this, do not skip steps in your head; "quota multiple" = today's increment / baseline):
  - **Trigger**: baseline 4%, today's increment 12% (3 times, more than 2 times); average daily task count over the last 7 days is 6, so the task-count threshold = 6 x 3 / 2 = 9; today's task count is 2, less than 9 -> trigger.
  - **No trigger (workload kept up)**: same baseline 4%, increment 12%, threshold 9; today's task count is 10, not less than 9 -> no trigger.
  - **No trigger (did not exceed 2 times)**: baseline 4%, today's increment 6% (1.5 times) -> no trigger.
  - **Only list (not enough samples)**: only 3 valid increments in the last 7 days, today's increment is 20% -> only list that day's consumption in the findings, no trigger.
